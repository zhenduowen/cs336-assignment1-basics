BPE training: profiling comparison

The optimized trainer is faster on all three tested workloads. Every measured run produced the same vocabulary and ordered merge list.

Python 3.12.12 · Linux-6.6.87.2-microsoft-standard-WSL2-x86_64-with-glibc2.39 · 16 logical CPUs visible

Method

Three unprofiled runs per variant, alternating naive/current execution order; median elapsed time around train_bpe only. Imports and output comparisons are outside timing. Both trainers receive a small warmup, and each input is read for its hash before timing, so these are not cold-disk benchmarks. The direct comparison uses one preprocessing worker. cProfile runs separately.

The saved naive source matches the committed HEAD version: True. The production trainer was not changed during this comparison. Peak memory was not measured.

Does the heap itself help?

A benchmark-only variant keeps integer IDs, unique pre-token counting, incremental pair counts, and the affected-word index, but replaces heap selection with a full max() scan. It removes heap maintenance and changed-pair bookkeeping. It is compared with fresh, alternating heap controls after profiling; outputs are checked exactly.

InputIncremental + max()Incremental + heapHeap speedup
TinyStories 5 MB sample0.662 s0.398 s1.66×
TinyStories validation9.671 s1.414 s6.84×

This experiment isolates the selection strategy. The original-versus-current comparison measures the other changes together; it does not assign independent speedup factors to every optimization.
